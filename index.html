Where it lands. Decode is about 4% slower and prefill about 8% slower than Hugging Face. That gap is the price of the simple design: every layer gathers pages into contiguous K and V before attention. This stage was built for correctness first, and it is the base for batching and a paged-attention kernel.

Chat reuse. In a multi-turn run, turn 2 reused 548 cached tokens and prefilled only 15 new ones, then generated 651 tokens in 23.15 s, about 28 tok/s overall. The time saved against --no-reuse has not been measured yet.

Bugs the tests caught

Two bugs that would have produced plausible but wrong output. Both were found by tests, not by reading generated text.

Stale data in reused int8 pages

A new sequence inherited a scale from the previous one and came out corrupted.

What happened

Freeing a sequence returns its pages to the pool but does not erase them. In int8 mode each page has one scale set by its largest value. A reused page still held the old sequence's values, so the scale came out too large and the new sequence was quantized too coarsely. The lifecycle test showed an error of 1.294.

How it was found

The free-then-reuse case in test_cache_lifecycle.py compared the reused cache against a dense reference.

The fix

_reset_page now zeroes the page and resets its scales to 1 every time a page is handed out. truncate also zeroes the leftover slots of the last kept page, so a shortened sequence cannot leak old values into its scale.

What it taught

Any cache that reuses memory needs to treat "free" and "clean" as different states. In float modes stale slots are overwritten before they are read. With per-page scales they are not harmless.

Follow-up chunks could see the future

With a cached prefix, new tokens were allowed to attend to tokens after them.

What happened

Attention has three cases. A full prefill uses is_causal=True. A single decode token needs no mask. A follow-up chunk, with 1 < T_q < S (several new queries against a longer cache), fell through to the wrong handling, so a query could attend to keys that come after it in the chunk.

The fix

An offset boolean mask: query i may see keys up to position S - T_q + i. This was fixed before chat reuse was added, since reuse is exactly what produces these chunks.

What is mine, what is not, and what is next

The cache, attention, generation loop, sampling, chat reuse, tests and benchmark are written here. Weights, embeddings, RMSNorm, MLP, projections and the RoPE tables come from Hugging Face layers. One sequence runs at a time.

Limitations today

  • One sequence at a time. Write and gather take a single slot.
  • Gather copies the whole cache every layer and step. Long contexts slow down.
  • int8 uses one coarse scale per page. An outlier sets the step size for the block.
  • No stop strings and no automatic dropping of old chat turns.
  • A failure mid-step leaves pending tokens set until /reset.
  • Open item: an HF comparison matched 40 of 51 tokens, splitting after 5 generated tokens. Likely an fp16 near-tie, not yet proven. A teacher-forced logit check is the next step.
  • The follow-up test suite is written but its result is not yet confirmed.

Roadmap

  1. Run the logit check and follow-up tests, and measure chat reuse against --no-reuse.
  2. Benchmark 2048-token prompts to measure the cost of gather.
  3. Batched decode, tested so a batch matches each sequence run alone.
  4. A scheduler: request queue, continuous batching, admission by free pages, preemption.
  5. Prefix caching across requests, a paged-attention kernel, CUDA graphs, an OpenAI-compatible API server.
